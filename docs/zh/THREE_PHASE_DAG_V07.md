# v0.7：三阶段研究主轴 × 全局方法演化 DAG

这份设计用于解释 **Physics AI Methods Atlas** 如何同时表达两种不同的知识：

1. **科学研究主轴**：研究任务需要什么能力。
2. **方法演化图**：方法由什么前驱发展而来，解决了什么技术瓶颈。

它们通过有说明的功能映射联系，但绝不把“可用于某环节”误认为“历史上由该环节演化产生”。

## 一、三个研究阶段

| 顶层阶段 | 对应原有子能力 | 研究问题 |
|---|---|---|
| Ⅰ 物理系统建模与正向问题 | `stage.physics-forward`、`stage.observation` | 建立控制方程、参数化、边界条件、正向求解器和观测映射 |
| Ⅱ 反问题求解与未知信息推断 | `stage.inverse-calibration` | 从有限含噪数据估计未知参数、边界条件和隐藏状态，处理正则化及可辨识性 |
| Ⅲ 个体化预测、干预与闭环更新 | `stage.prediction-uq`、`stage.intervention-planning`、`stage.continual-update` | 在新条件下预测、开展反事实模拟与规划，并利用新观测反馈修正模型 |

这不是三步必须严格执行的程序。正向模型会被反演与预测重复调用；新的观测可能引发第二阶段的重新推断、甚至第一阶段的模型修正。数字孪生和世界模型是相关的**系统能力和研究方向**，不能与所有预测方法等同。

**正则化**主要用于阶段Ⅱ的稳定反问题求解；第一阶段可以预先定义物理约束和先验。**物理一致性、可辨识性、数值与模型误差、不确定性以及外部验证**都是贯穿三个阶段的要求，而不只属于某一步。

三阶段的中文/英文标签、子能力映射与固定配色存放于 `config/v07.json`。v0.3 已有的六个子能力 ID 不删除，已有的论文/方法功能关系也不重写。

## 二、DAG 的严格含义

| 关系 | 可否作为分层布局依据 | 图中如何表现 |
|---|---|---|
| `extends` | 是 | **有证据支持**的扩展，实线、有向、使用所针对阶段的颜色 |
| `combines` | 是 | 技术融合，有向虚线，颜色同上 |
| `specializes` | 是，但只是辅助分类 | 中性灰色点线，不被当作历史改进 |
| `contrasts_with` | 不参与 DAG 排序 | 可选对照线、默认隐藏 |
| `uses_method` | 不属于方法谱系 | 在上方“阶段 → 方法/家族”卡片中说明实际功能 |

方法扩展与融合构成 DAG；在当前数据中，加入分类边后仍然无环。Graphviz `dot` 会对真实的这组关系进行分层布局和路径计算，而不是先把方法塞入固定区块再连接。

**独立节点和不连通分量是正常且允许的。** 当前收录的论文尚未为所有方法提供历史谱系边，不能为了绘图效果凭空增加继承关系。

## 三、节点、边两套配色

- **节点的主要颜色**反映展示层面的技术范式：传统数值与优化（蓝灰）、统计与概率推断（淡紫）、机器/深度学习（青绿）、物理–数据混合（橙色）。
- **演进/融合边的颜色**反映所解决问题对应的顶层研究阶段：Ⅰ蓝、Ⅱ紫、Ⅲ青绿。无法明确主要阶段时使用中性灰。
- 分类边始终中性色；线型区分“扩展”和“融合”。较新的方法**不保证在所有指标上更优**。

一个方法允许具有多个真实家族标签。节点只有一个**主要显示色**，不意味着学术上只能属于一个家族。颜色规则是独立的显示配置，不覆写方法定义和文献关系。

以 **FNO → PINO** 为例：原论文支撑的物理残差约束训练，主要面向阶段Ⅰ，因此这条扩展边用蓝色；该方法在其他阶段的适用性通过功能映射和次要标签另行说明。

## 四、主轴到方法的功能关系

点击任意顶层阶段，系统聚合该阶段下子能力已有的功能映射：

- **直接关系：** 研究环节指向具体方法，显示原始的证据级别。
- **家族级关系：** 指向方法家族；其成员方法是值得研究的候选，**并不意味着每个成员都经过验证**。
- **上层家族关系：** 从更宽泛的家族层级导出的关联，显示更弱的高亮。
- **尚未建立映射的节点：** 暂时淡化而非删除；缺少关联记录不证明该方法与问题无关。

一个研究阶段可能对应好几个不连通的子图，不能为使其连通而添加假的前驱关系。

## 五、节点和边都能查看证据

**选择方法：** 突出该方法及邻近谱系节点，在详情中展示核心机制、多个家族归属、三阶段用途、可选 Start Here、Landmark 和原始数据文件。

**选择演进边：** 突出前驱和后继，展示具体技术变化、目标瓶颈、代价、关联研究阶段及支持论文。点击分类边则仅解释分类关系，不虚构技术突破。

图上默认不贴满长段文字；实际学术说明在右侧详情中，以减轻交叉线的视觉负担。

## 六、技术实现与测试

`config/v07.json` 记录阶段与范式。`scripts/build_v07.py` 从现有权威图谱投影读取全部方法与有类型关系，使用 **Graphviz `dot -Tsvg`** 自动进行 DAG 分层布局。输出的 SVG 中每个方法/边都带有稳定的权威 ID，供点击和查询。

构建命令：

```bash
python -m pip install -r requirements-dev.txt
python -m scripts.build_v07 --site build/viewer-v07
```

**构建时需要 Graphviz 和支持中文的字体**；导出的 `build/viewer-v07/index.html` 已嵌入 SVG 与 JSON，连同 `app.js`、`style.css` 解压后可离线打开，不需 Graphviz 或服务器。

GitHub Actions 会执行数据一致性和无环校验、运行 JavaScript 检查、在 Chromium 中进行桌面与手机交互测试，并导出布局截图。

这仍是 **v0.7 交互原型**，尚未在 GitHub Pages 上正式上线。若用户认可布局，再完善成可持续部署的大规模知识图谱。
